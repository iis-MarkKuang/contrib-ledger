# Workflow

做需求之前先有 `SOLUTION.md`，再拆 ticket，再按 `ROADMAP.md` 做。不要跳过方案直接改代码。

## SOLUTION.md

一份，放仓库根目录。至少包含：

- 架构：谁持有状态，谁签名，谁付钱上链
- 依赖库：名字和用途。没写进去的库不要装
- 关键流程的时序图，用 Mermaid `sequenceDiagram`

方案改了，先改 `SOLUTION.md`，再改受影响的 ticket。不要只改代码。

## Ticket

目录：`tickets/Txx-短名.md`。一张票只做一件事。做完才能开下一张未完成且依赖已满足的票。

每张票都要有这六节：

```markdown
# Txx 标题

## 目标

## Non-goals

## 约束

## 上下文

## 测试验证

## 完成状态
```

- **目标：** 做完后多了什么可观察行为。
- **Non-goals：** 这张票明确不碰的目录、合约函数、页面。
- **约束：** 红线。碰到私钥、地址、gas、范围变更、新依赖、新 MCP、登录第三方 CLI 时停下来报备，不要做完再讲。
- **上下文：** 依赖哪些票，挡住哪些票。
- **测试验证：** 具体命令或点击路径。没跑过不能把状态改成完成。
- **完成状态：** `未开始`、`进行中`、`完成`、`阻塞`。完成时写验证命令的结果，不要只改标签。

## Roadmap

`ROADMAP.md` 只排序和标状态，不复制票的正文。做的时候改票里的状态，并让 roadmap 表和它一致。

弹性项（需求里的社区挑战）留在 roadmap 末尾，状态保持 `未开始`，直到前面的闭环票完成并且用户确认还有时间。
